# Plan: Cluster photos by similarity, label groups with AI

**Status:** clustering core prototyped and validated against a real library. UI, persistence, and labeling not yet built.
**Branch:** `claude/kmeans-photo-clustering-27125f`

A new photos view that groups photos by what's in them, with a slider controlling how many groups. Each group gets a name generated by showing a vision model the group's most representative thumbnails.

---

## 1. What the prototype settles

The open question was never "can we run k-means" — it was **"are Qwen3-VL retrieval embeddings good enough to cluster a personal photo library semantically?"** Retrieval embeddings are trained to match images against text queries, not to partition an image set, and the failure mode to worry about was clusters forming around palette and exposure ("all my dark indoor photos") rather than subject.

**That failure mode did not occur.** Run against the live dev library (2,808 embedded photos), groups at k=20 came out as:

| | |
|---|---|
| Colosseum exteriors | 263 photos, coherence 0.75 |
| Mountain village in a valley | 321, 0.79 |
| Lake with boats and shoreline towns | 286, 0.77 |
| Coastal village on terraced cliffs | 234, 0.79 |
| Alpine slopes and rocky peaks | 249 / 183, 0.82 |
| Swans on water | 123, 0.77 |
| Other waterbirds (coots, ducks, cormorants) | 103, 0.74 |
| Grand palace exteriors (Schönbrunn, Versailles, Vaux-le-Vicomte) | 97, 0.84 |
| Cathedral / ornate interiors | 81, 0.78 |
| Youth baseball | 117, 0.51 |
| Wedding and bridesmaid groups | 105, 0.55 |
| Family in kitchens and living rooms | 97, 0.57 |
| Night skyline: tower and lit bridge over water | 107, 0.58 |

These are subject-level groups, and they split at exactly the granularity a user would want. The model distinguishes swans from other waterbirds, and palace exteriors from cathedral interiors, without being asked to.

Email-attachment graphics from the PST import separated cleanly from real photography into their own groups — website nav bars and banners, solid-black spacer images, image macros, and adult content — at 78–100% source purity. The clustering does the junk triage for free.

**Conclusion: the feature works. Build it.**

### Measured behaviour

Library: 2,808 image embeddings × 2,048 dims (21.9 MB). MacBook, `dart run`, single isolate, no PCA.

| Metric | Result |
|---|---|
| L2 normalise all rows | 10 ms |
| Build full tree, 48 groups | 3,195 ms |
| Re-cut tree for a new k | 11–28 µs |
| Scaling in n (1,404 → 2,808) | 1,544 → 3,195 ms — **linear** |
| Scaling in k (16 → 96 groups) | 2,410 → 3,583 ms — **logarithmic** |

Slider stability, the property bisecting k-means exists to provide:

| Slider move | Photos that stay in the same group |
|---|---|
| k=7 → 8 | 71.6% |
| k=19 → 20 | 92.0% |
| k=39 → 40 | 95.6% |

At useful k values, dragging one notch leaves >90% of the grid untouched. Flat k-means would reshuffle arbitrarily at every notch.

## 2. What was built

### `client/lib/modules/photos/services/clustering/spherical_kmeans.dart`

The real algorithm, production-bound. Pure Dart over `Float32List` — no plugins, no database, no Flutter binding — so it runs unchanged in an isolate or a `dart run` harness.

- `l2NormalizeRows` — scales rows to unit length in place.
- `buildClusterTree` — bisecting spherical k-means; returns a `ClusterTree`.
- `ClusterTree.leavesAt(k)` — the k groups, as a pure tree walk. This is what the slider calls.
- `ClusterTree.representatives(node, data)` — the members closest to a group's centroid, i.e. the thumbnails to send the labeling model.

Covered by `client/test/modules/photos/spherical_kmeans_test.dart` (9 tests, passing). The tests encode the invariants the feature depends on, not just arithmetic: that every k partitions the library exactly once, that k+1 refines k rather than reshuffling it, that a given seed always produces the same tree, and that a set of identical vectors refuses to be split rather than emitting empty groups.

### `client/tool/photo_clustering/`

Prototype harness, not shipped code.

```bash
python3 tool/photo_clustering/dump_vectors.py /tmp/dump --type file
dart run tool/photo_clustering/run_prototype.dart /tmp/dump --k 8,20,40
```

`dump_vectors.py` reads the app database read-only and writes a flat `vectors.f32` plus a `meta.tsv`; the Dart harness clusters it and prints each group's size, coherence, source mix, and the captions of its most central members. Captions are the only readable signal — a real library's filenames are almost all `IMG_1234.heic`.

## 3. Decisions the prototype locks in

**Spherical, not Euclidean.** Qwen3-VL is trained under cosine similarity, and the app already assumes unit vectors — `findSimilarImages` converts distance to a percentage with `(1 - d/2) * 100`, which is only a similarity if `|x| = 1`. Rows get normalised; every comparison is a dot product.

**Bisecting, not flat.** Driven entirely by the slider. See the stability table above.

**Cluster the image embedding (`type='file'`), not the caption embedding (`type='description'`).** Both exist in the database, so this was tested head to head. Image embeddings won: higher coherence on the large groups and better source purity, where the caption run produced one badly mixed group (50% purity). Captions also collapse distinct photos to cosine 1.0000 when the model writes them the same sentence, which destroys duplicate detection. This drops a whole dependency — no captioning pass required before clustering.

**No PCA yet.** Dimensionality reduction to ~128 dims would cut build time ~16×, but at 2,808 photos the full 2,048-dim build takes 3.2 seconds in a background isolate. Since cost is linear in n, the projection is ~57 s at 50k photos and ~2 min at 100k. Add PCA when a real library crosses roughly 25k photos; don't build it speculatively. The lever is known and the measurement is here.

**Duplicates stay a separate feature.** A within-leaf scan at cosine ≥ 0.98 found 1,649 pairs across 1,501 photos — including obvious burst sequences (`DSC_1818`/`DSC_1819`/`DSC_1820` at 0.986–0.991). Duplicates do land in the same cluster, but a cluster is far broader than "the same photo," so surfacing duplicates means thresholding, not partitioning. Note also that `files` has **no content hash column**, so even byte-identical copies currently have to be found through embeddings; a hash column would be cheaper and exact, and is worth considering independently.

## 4. Still to build

### 4.1 Schema

Two tables, hand-written DDL in `AppDatabase.schemaDDL` per the project's no-codegen convention.

```sql
CREATE TABLE IF NOT EXISTS photo_cluster_runs (
  id TEXT PRIMARY KEY,
  collection_scope TEXT,          -- NULL = whole library
  created_at INTEGER NOT NULL,
  photo_count INTEGER NOT NULL,
  max_groups INTEGER NOT NULL,
  seed INTEGER NOT NULL,
  status TEXT NOT NULL            -- building | ready | stale
);

CREATE TABLE IF NOT EXISTS photo_cluster_nodes (
  run_id TEXT NOT NULL,
  node_id INTEGER NOT NULL,
  parent_id INTEGER,
  split_rank INTEGER,             -- position in splitOrder; NULL if never split
  member_count INTEGER NOT NULL,
  coherence REAL NOT NULL,
  centroid BLOB NOT NULL,         -- Float32, dim 2048
  label TEXT,
  label_status TEXT NOT NULL DEFAULT 'pending',
  PRIMARY KEY (run_id, node_id)
);

CREATE TABLE IF NOT EXISTS photo_cluster_members (
  run_id TEXT NOT NULL,
  node_id INTEGER NOT NULL,
  file_id TEXT NOT NULL,
  PRIMARY KEY (run_id, file_id)
);
```

Storing `split_rank` is what makes the slider a database query rather than a re-run: the k groups are the leaves after replaying splits `0..k-2`.

Interior nodes keep their members and their labels. A label computed for a node stays valid at every k where that node is a leaf — that is the whole payoff of the nested structure, and it is why labeling cost is bounded by tree size rather than by (number of slider positions × k).

### 4.2 Clustering isolate

Follow the existing `EmbeddingIsolate` pattern in `client/lib/modules/files/services/embedding_isolate.dart`: its own `AppDatabase` connection for reads, all writes relayed to the main isolate over the control port. Per `CLAUDE.md`, isolates never write through their own connection.

1. Read `(file_id, qwen3_vl_embedding)` for images where `type='file'`, `is_deleted=0`, `is_inline=0`.
2. Pack into one `Float32List`, `l2NormalizeRows`, `buildClusterTree`.
3. Relay nodes and members to the main isolate for persistence.
4. Post progress so the UI can show a determinate bar; the existing `onProgress` callback reports leaves built vs. target.

Pause while any scanner is syncing, as the embedding isolates already do.

### 4.3 Labeling

One `POST /v1/chat/completions` per node, with the top ~6–9 representatives as OpenAI multimodal content parts.

Image bytes: read the local file and base64-encode it, the same path `_generateEmbedding` uses. **Do not use `files.thumbnail`** — that column holds a remote provider URL (Google Drive `lh3.googleusercontent.com` links), not local bytes, so it is both empty for most photos and a network call against the local-first design. Route bytes through `POST /util/thumbnail` first to downscale; vision token cost scales with image area and there are ~9 images per request.

Use `response_format` with a JSON schema — `routes.py` grammar-constrains local GGUF generation — so labels come back as structured `{"label": "...", "confidence": ...}` rather than prose to be parsed.

Throughput is the constraint: `state.generation_lock` serialises generation, so labels must arrive progressively. Show "Group 4" immediately and swap in the real label when it lands. A 48-node tree at ~5–15 s per call is several minutes of background work.

Cache on `(run_id, node_id)`. Nodes are immutable within a run, so a label is computed at most once.

### 4.4 UI

- Add `clusters` to `PhotoViewMode` in `view_state_service.dart` (currently `{grid, list, map}`).
- The view maps onto the existing sectioned-sliver structure — group label as section header, same `SliverToBoxAdapter` approach `PhotoGrid` already uses for date headers.
- Slider bound to `maxGroups` from the run. Re-cutting is a tree walk in microseconds, so it can update on drag rather than on release.
- Surface coverage honestly. The library has 2,872 images but only 2,808 embeddings; `getFilesWithMissingEmbeddings` exists because embedding is a slow backfill. A cluster view that silently omits un-embedded photos is worse than one that says "clustering 2,808 of 2,872 — 64 still processing."

**Cluster scope follows the active source filter.** The cluster view is a view, not a different library — it shows exactly the set the drawer is currently showing, the same as grid, list, and map do. "All Photos" clusters everything from every source: local disk, Google Drive, Gmail, Yahoo, Outlook, PST archives, and social sources as they land. Selecting a single source clusters only that source — pick Gmail and you cluster Gmail's attachments and nothing else.

This is the point of the product: one gallery spanning every place a photo might live. The clustering must not quietly carve out a source it thinks the user didn't mean, and there is no default that excludes email attachments.

Practically this means a run is scoped by the filter that produced it. `photo_cluster_runs.collection_scope` already carries this: `NULL` for All Photos, otherwise the selected collection ids. Switching sources means selecting a different run (or building one), not re-filtering an existing run's members — a tree built over the whole library and then filtered down would leave groups that are mostly empty and labels that describe photos no longer shown.

Caching implication: each distinct scope is its own run with its own tree and its own labels. Build lazily on first use of a scope and keep the most recent few, rather than precomputing a run per collection.

### 4.5 Cleanup: restore delete to the selection header

Clustering turns out to be a strong junk-triage tool. The PST import contributes 436 images to the library — website nav bars, banners, solid-black spacer GIFs, image macros — and they collect into their own groups at 78–100% source purity. Select a group, delete it, and a quarter-century of email chaff leaves the gallery in one action. The shift-click range select and batch actions shipped in `ba120cc` are already the right tooling.

**Restore the Delete icon to the batch-selection toolbar** in `photos_toolbar.dart`. It was removed in `d933597` along with the sidebar's Delete and Open in Finder buttons; the confirm-dialog + `BatchActionService.deleteSelected` path it called still exists and is still reachable from the Delete/Backspace shortcut in `keyboard_shortcut_handler.dart`. Restoring the button is re-adding an `IconButton`, not rebuilding a feature.

Three things about delete need to be understood before this is called a cleanup feature, because the current behaviour does not match what "delete the email attachments" sounds like.

**1. Delete is soft, and only touches the database.** `BatchActionService.deleteSelected` runs `UPDATE files SET is_deleted = 1` and nothing else. No file is removed from disk, no attachment is removed from any email, and no disk space is reclaimed. It hides rows from the gallery. That is a defensible default — this is an archive tool, and destroying a user's originals from a photo grid would be the wrong instinct — but the button's label should not promise more than it does. "Remove from gallery" is honest; "Delete" implies the file is gone.

**2. Rescans resurrect deleted photos.** `FileRepository`'s upsert ends with `ON CONFLICT(id) DO UPDATE SET ... is_deleted = 0` ([file_repository.dart:273](../../client/lib/modules/files/services/repositories/file_repository.dart:273)). The next scan of a collection clears the flag on every row it sees. So:

- PST-imported junk — the 436 images actually at issue — **stays deleted**, because PST import is a one-time isolate invoked from the UI and is explicitly not a registered scanner (`scanner_manager.dart:285`). Nothing re-runs over it.
- Gmail, Yahoo, and Outlook IMAP attachments **come back on the next sync**. Local filesystem and Google Drive photos come back on the next scan.

For local files that is arguably correct: the file is still on disk, so it should reappear. For a cleanup workflow it makes the feature feel broken — the user deletes 200 banner images from Gmail and they return within the hour.

The cause is one column carrying two different meanings: "the source no longer has this" (owned by the scanner) and "the user does not want to see this" (owned by the user). They need to be separate. Add a user-owned column that the scanner upsert never touches:

```sql
ALTER TABLE files ADD COLUMN is_hidden INTEGER NOT NULL DEFAULT 0;
```

`deleteSelected` sets `is_hidden = 1`; every photos query adds `AND is_hidden = 0`; the upsert continues to manage `is_deleted` alone. Cleanup then survives sync for every source, and the existing reappear-on-rescan semantics for genuinely restored files are preserved. This is a small change and it is the difference between the cleanup story working and not working.

**3. Embeddings outlive the delete.** `files_embeddings` rows are not removed by a soft delete, so a hidden photo keeps its 8 KB vector. Harmless for correctness — the clustering isolate filters on the visibility flags, so hidden photos are excluded from runs — but a library cleaned of 400 images keeps 3 MB of dead vectors. Worth a periodic sweep, not worth blocking on.

**Open question for the UI:** deleting a whole group from the cluster view is a large, mostly-irreversible-feeling action. The confirm dialog should say how many photos and from which sources, and there should be a way back — either an "undo" snackbar or a Hidden/Trash view that lists `is_hidden = 1` rows and can restore them. A cleanup tool with no undo is one misclick from losing photos the user cared about.

### 4.6 Keeping it current

Scanners add photos continuously; a run is a snapshot. Assign new photos to the nearest existing centroid — one dot product per centroid, negligible — and mark the run `stale` past a threshold of newly-assigned photos, with an explicit "regroup" affordance. Do not attempt live re-clustering: it would invalidate every cached label on every scan.

## 5. Risks and open questions

**Junk and sensitive content surface as first-class groups.** *Resolved — the cluster view shows whatever the source filter shows, with no source excluded by default (§4.4).* Worth stating what that means in practice: these images are already in the photos grid today, since `photos_repository.dart` filters only on inline/deleted/content-type and never on source. Clustering does not add them; it gathers them. Content that was invisible because it was scattered chronologically — including a 52-photo group of adult content from the 1998/1999 PST archives — becomes a labeled group. That visibility is the cleanup feature working as intended (§4.5), but it is a change in what the gallery looks like on first open, not a neutral refactor.

**Labeling adult or borderline groups.** A local vision model may refuse, hedge, or produce an awkward label. Needs a graceful fallback to an unlabeled "Group N" rather than an error state or an empty header. Since no source is filtered out, this path will be exercised on a real library rather than being a theoretical edge case — treat the fallback as required, not defensive.

**Coherence varies widely (0.46–0.84).** Tight groups (palaces, alpine peaks) will label well. Loose groups — the 0.46 group mixing living rooms, wedding guests, and kitchens — are genuinely heterogeneous, and a single label will misrepresent them. Consider surfacing coherence in the UI (a "mixed" marker), or auto-splitting below a threshold.

**Seed stability across runs.** `buildClusterTree` is deterministic given the same data and seed, but adding photos changes the data and therefore the tree. Cached labels are keyed per run, so this is handled — but it does mean a regroup discards label work. Worth measuring how much labels actually change before deciding whether to try transplanting them across runs.

## 6. Phasing

| Phase | Scope | Exit criteria |
|---|---|---|
| 1 ✅ | Clustering core + prototype harness | Semantic groups verified on a real library; tests pass |
| 2 ✅ | Schema + clustering isolate + persistence | A run completes end-to-end and survives restart |
| 3 | Cluster view + slider, unlabeled groups, scoped by source filter | Slider is smooth at ≥40 groups; All Photos and a single-source selection each cluster correctly; coverage shown honestly |
| 4 | Vision labeling with progressive fill-in | Labels land for every node; refusals degrade gracefully |
| 5 | Incremental assignment + stale/regroup | New photos land in a group without a full rebuild |
| Later | PCA to ~128 dims | Only once a real library passes ~25k photos |

**Cleanup track (§4.5) — independent of the clustering phases, shippable on its own:**

| Step | Scope | Exit criteria |
|---|---|---|
| C1 ✅ | `is_hidden` column; `deleteSelected` writes it; photos queries filter on it | A hidden photo stays hidden across a full rescan of its collection |
| C2 ✅ | Restore Delete icon to the batch-selection toolbar | Selecting photos and confirming hides them; count and sources shown in the dialog |
| C3 | Undo affordance or a Hidden view with restore | A deleted group can be brought back without touching the database by hand |

C1 should land before C2. Shipping the button first gives the user a cleanup action that silently reverts on the next email sync, which is worse than not having the button.

database and asserts that centroids survive the port as unit vectors, that the
persisted grouping is the one the data implies, that a collection scope is
honoured, and that hidden photos are excluded:

- ✅ `PhotoClusterRepository` — scoped embedding load, run persistence, tree and
  membership reload, subtree resolution, label writes, run pruning.
- ✅ `ClusteringIsolate` — reads through its own connection, relays the finished
  tree to the main isolate to write, per the isolate write rule.
- ✅ `PhotoClusterService` — reuses a ready run for a scope or builds one, holds
  the slider position, buckets photos into groups.
- ✅ Round trip — the real isolate spawns, opens its own connection to the same

The invariant worth protecting is covered: a test asserts that the tree
rehydrated from the database reproduces the algorithm's grouping at every k. If
that ever breaks, the view silently shows a different grouping than the one that

scanner upsert path over that row, and asserts it stays hidden.
